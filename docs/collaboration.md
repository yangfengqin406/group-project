## 每个任务的流程

先运行 `git status`；有未提交改动时先在当前分支保存并提交，再切换到本人的固定工作分支。以下以A为例；B/C替换为表中自己的分支，新电脑首次使用时先fetch并建立对应远程跟踪。

```bash
git switch codex/a-plaza-partner-pets
git pull --ff-only
# 修改、验证
git add <改动的文件>
git commit -m "feat(plaza): 更新广场功能"
git push origin codex/a-plaza-partner-pets
```

在 GitHub 提 PR，由另一位队友检查接口影响和验收结果后合并。不要直接往 main 推日常功能；仓库管理员需在 GitHub Settings 中实际启用 main 的保护规则，文件本身不会自动开启保护。

PR合并后仍保留A/B/C三个工作分支。需要查看团队整合版时保存本地工作、切main并pull；继续开发时回本人的工作分支，按团队协调同步main。每天检查是否有可审阅的整合成果，确保main能运行。出现冲突先看双方改动并沟通，不要直接选“全部保留我的”。解决后重新执行检查与两端构建。

- 日常工作使用表中的人员分支，小步提交；确需临时分支时说明用途与清理时机，不擅自增加或删除人员分支。
- 提交前检查 git diff；不要提交 node_modules、dist、令牌、AppSecret 和 .env。
- package.json、package-lock.json、pages.json、manifest.json、请求层改动需提前通知调用方。新增页面由改动者登记路由并检查 tabBar。
- 依赖版本锁定；队友默认 npm ci，新增依赖由一人统一处理，不各自升级。
- 提交信息用 feat/fix/docs/chore；不要只写“修改”或“更新”。

## 文档更新与进度记录

每个任务的代码作者负责更新受影响的文档，并填写 PR 模板。让 Codex 完成代码时一起检查文档影响；相关文档和代码在同一个 PR 中提交。没有相关变化的文档不必修改，在 PR 的“文档同步”栏说明无需更新的原因。

| 本次变化 | 需要检查或更新的位置 |
| --- | --- |
| 安装、启动、使用方式、目录或依赖要求 | README.md；涉及部署时检查 docs/deployment.md |
| 功能范围、业务规则或验收方式 | docs/requirements.md、docs/acceptance.md |
| 接口参数、返回值、公共数据字段或状态流转 | docs/interfaces.md、docs/data-model.md；同步对应服务与调用方 |
| 全局画风、组件规范或交互约定 | docs/design.md |
| 负责人、公共文件维护人或协作流程 | docs/collaboration.md；需要工具遵守的规则同步 AGENTS.md |
| 任务完成状态、实现边界或待联调事项 | 在 PR 中报告；由 A 汇总 docs/status.md 和 tasks.csv |

B/C 在各自 PR 写清任务编号或模块、完成情况、剩余工作和验证依据。A（集成负责人）每日根据合并的 PR 更新总进度；只通过构建、本机演示或单模块验证的功能，不标记为真实后端和跨设备联调全部完成。需要其他队员直接编辑总进度时先协调，按对应条目修改。

审核人合并前检查三件事：代码与文档是否一致、PR 是否说明本次变化及剩余工作、验证是否实际执行。AGENTS.md 和模板负责提醒，现有检查脚本不会自动判断文档语义是否正确。

新规则合并后，每个人先保存并提交当前任务改动，再同步仓库。在开始下一次 Codex 任务时要求它重新读取 AGENTS.md 和本次相关文档；旧会话不能仅凭已有上下文推断最新规则。
