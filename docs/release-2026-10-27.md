## 交付定位

按用户确认“暂无服务器/域名，先完成部署包与展示版；真实版必须含完整小游戏和衣柜”。当前源码包括真实校园业务、原创宠物、完整钓鱼/三关潜水/衣柜持久化，以及独立访客三人斗地主。没有删减玩法或把接口失败改为演示成功。

Windows 展示包内带 Node22.22.0 与官方许可证，不需 npm 安装；代码部署包不带 Windows 运行时，供安装 Node22 的服务器使用。两包均不带真实用户数据库、上传、令牌、AppID 或私有配置。首次展示启动才在本地生成虚构数据及随机测试密码，正式服务不会自动灌入样例。

产物生成位置：`dist/deliverables/`。`campus-deploy-20261027.zip` 为部署代码包，`campus-windows-showcase-20261027.zip` 为便携展示包；包内 `release.json` 记录源码/构建文件 SHA256。演讲、流程、故障处理见 [展示手册](showcase-2026-10-27.md)。

## 本机展示

完整解压 Windows 包，双击“启动展示.cmd”，保留终端，打开 `http://127.0.0.1:8791/#/`，凭包内 `.showcase-campus/展示账号.txt` 登录。只监听回环地址，不把校园 Wi-Fi 设成专用网络，不改防火墙，也不依赖校园网设备互访。不要双击 `index.html`；页面需要 HTTP 服务。

展示角色和第一关预置奖励明确为虚构数据；实际认证、文件、消息与后续玩法调用真实 SQLite。旧 `.local-campus` 不受影响。第二次启动保留上次操作；需要全新排练数据时，指定一个**新的空目录** `CAMPUS_SHOWCASE_DATA_DIR`，不要删除真实数据目录。

源码中运行：先在 Node22 下执行 `node scripts/build-release.mjs`，固定使用 `VITE_API_MODE=http`、H5同源 `/api` 与 `VITE_GAME_BASE_URL=/game`，两端输出至 `dist/release`，再执行 `node scripts/start-showcase.mjs`。源码启动可读取仓库公开头像；完整包自带配图。随后用 `node scripts/package-release.mjs` 生成部署目录，已存在的目录不覆盖；默认微信接口为本机8791，正式构建前设置 `CAMPUS_RELEASE_WECHAT_ORIGIN` 为实际HTTPS源。

## 服务器部署：单机 Node22 + SQLite + Nginx

当前没有可操作的公网环境，下列为部署步骤与配置模板，**未在实际 Linux/公网 TLS 环境验收**，不写成已经上线。服务器采用单实例，SQLite 与文件同盘，勿多副本无共享存储。应先使用测试域名与空数据验证，成功后再公开邀请。

1. 安装 Node22.22.0 和 Nginx。将代码包内容置于 `/opt/campus`，确认 `/usr/bin/node --version` 是22。运行时只用 Node 内置模块，无需复制 node_modules。
2. 创建专用低权限账号 `campus` 和 `/var/lib/campus`，目录仅该账号可写。不要把上传、数据库放进静态目录；不要复制本机展示账号到正式目录。
3. 复制 `deploy/campus.env.example` 到服务器私有 `/etc/campus.env`，改成实际 HTTPS 源，权限设为600。`CAMPUS_PUBLIC_ORIGIN` 只允许 HTTPS 源，不含路径；`CAMPUS_TRUSTED_PROXIES` 只填写实际直连代理 IP，本模板为本机127.0.0.1、::1。默认不信任客户端转发头。
4. 检查后安装 `deploy/campus.service`，核对服务用户、工作目录、Node路径和可写数据目录，再用 systemd 启用。后端只监听回环8788，公网不开放该端口。
5. 将 `deploy/nginx-campus.conf` 的域名与证书路径替换为实际值，先 `nginx -t`，通过后重载。模板覆盖客户端转发头，保留 Host，转发到127.0.0.1:8788；HTTP跳转HTTPS。反代行为依据 [Nginx 官方文档](https://nginx.org/en/docs/http/ngx_http_proxy_module.html#proxy_set_header)。
6. 在公网浏览器验证首页不降级HTTP、`/api/health`正常；两个独立账号注册/登录、上传发布、双向消息、邀请确认、小游戏及衣柜重登、退出登录均通过。上传地址必须为实际HTTPS域名，文件Cookie含Secure。用第二台物理设备再验一次。
7. 停止写入后成套备份数据库及 uploads；先在隔离目录做恢复演练，再升级。不要只复制运行中的 SQLite 主文件而遗漏 WAL。保留旧构建，回滚时先评估数据库兼容，不覆盖新用户数据。

应用已对明确HTTPS源、可信代理IP链、Secure文件Cookie、真实客户端登录限流与大PNG宠物请求补回归测试；这些代理帧测试不代替实际证书、Nginx、服务器防火墙或公网压力验证。
